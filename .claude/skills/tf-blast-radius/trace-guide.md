# Trace guide: where couplings hide

How to find whatever reads a changing value. These are search methods, not answers: always
confirm a coupling by reading the actual lines before you cite it.

Roots live in `infra/environments/<env>/<root>`, modules in `infra/modules/<category>/<module>`,
GitOps manifests in `gitops/`, and workflows in `.github/workflows/`.

## Terraform remote state readers

A root's outputs are read by other roots through `terraform_remote_state`.

- Grep `terraform_remote_state` across `infra/environments` to see which roots read which.
- Then grep `outputs.<output_name>` to find the exact lines that use the changing output.
- To find which output carries a value, look in the producing root's `outputs.tf`.
- An output that re-exports another root's output (`value = data.terraform_remote_state...`)
  passes the value on unchanged. Keep following it.

## Module inputs and outputs

A root passes values into modules and reads values back.

- In the root, find the `module "<name>"` block and its `source`, then the module's
  `variables.tf` and `outputs.tf`.
- A value passed into a module can come back out as a module output (`module.<name>.<output>`).
  Grep that expression in the root.
- One module can be used by several roots (dev and prod). Grep the module's `source` path to
  find them all.

## Files generated by Terraform

`local_file` (often with `templatefile`) writes files into the repo.

- Grep `local_file` and `templatefile`. Read `filename =` to learn which file is written, and
  the template arguments to learn which values end up inside it.
- The generated file is a product. Grep its path (and its file name alone) across the repo to
  find what reads it.

## Generated or hardcoded values under `gitops/`

Values from Terraform can appear in GitOps files, generated or typed by hand.

- Grep the changing value's current literal (an ID, ARN, name or CIDR), not just its variable
  name, across `gitops/`.
- A hardcoded literal won't update itself after an apply. It's an impact.

## ArgoCD Application references

ArgoCD Applications under `gitops/applications/<env>/` point at charts, paths and value files.

- Grep the path of any file you found above inside `gitops/applications`. Look at
  `valueFiles`, `$values/...` references and `path:` fields.
- The Application is what deploys the change to the cluster, so it's the consumer to report.

## Workflow `env:` values and scripts

Workflows can hardcode names and IDs, or read them from Terraform outputs.

- Grep the changing literal and the variable or output name across `.github/workflows/` and
  `scripts/`.
- A hardcoded literal in `env:` or a script goes stale when the resource is renamed.

## Duplicated tfvars

The same variable can be set separately in several roots' tfvars.

- Grep the variable name across `infra/environments/*/*/*.tfvars` (and `variables.tf` for
  defaults).
- What matters is a setting that **must agree** across roots: a name or ID that one root uses to
  find or refer to what another root created. If the PR changes it in only one root, the other
  now points at something that doesn't match. That's an impact.
- Settings that are independent per root (like each root's own tags map) don't need to agree.
  Differences between them are not impacts.
